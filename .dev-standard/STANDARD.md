# The team development standard

One page. Everything else in this repo exists only to make this page true in every repository with one command.

## Why

We are a small team, several people and four different coding agents (Claude Code, Cursor, Codex, OpenCode) touching the same code. The standard exists so that anyone — human or agent — can open any of our repos and know how work starts, how it is reviewed, how it is merged, and where decisions live. It is built from existing, maintained tools; we write as little of our own as possible.

## The workflow, per feature

1. **Explore, then propose.** `/opsx:explore` on the codebase, then `/opsx:propose <feature>` → `openspec/changes/<feature>/{proposal.md, design.md, tasks.md, explainer.html}`. `design.md` carries Mermaid diagrams of what the change touches; `explainer.html` is a self-contained page that explains the problem and the idea and animates how it works, step by step — open it in a browser. A big feature gets a 15-minute design review of the explainer and `design.md`; slides only if someone asks.
2. **Implement** with `/opsx:apply`, on branch `feat/<ticket>-<slug>`. The agent follows `AGENTS.md`; it never touches restricted paths; anything out of scope becomes a GitHub Issue (`gh issue create --label backlog`), never a fix in this PR.
3. **Open the PR as a draft.** The body opens with an _At a glance_ Mermaid diagram of what the diff touches, then `proposal.md` + `design.md` (its diagrams render on GitHub) pasted under the template headings, plus evidence: test run, `make pipeline` output, and for anything touching hardware a log or video from the real robot.
4. **Agent review first**, locally: your own coding agent runs the `pr-review` skill with a fixed rubric (scope matches proposal · tests for every new function, none removed · lint/type/ratchet green · restricted paths untouched · docs/ADR updated · out-of-scope findings filed as issues · no secrets or undeclared dependencies · diagrams match the diff and the design) and posts its table on the PR. No CI job and no API key. When every row passes, the PR is marked ready for review; humans see it only then.
5. **One CODEOWNER approves.** Docs-only PRs need only the agent review. No review SLA.
6. **Squash-merge**; PR title is the commit. CI regenerates the graph, the diagrams and the reference docs. `/opsx:archive` moves the change to `openspec/changes/archive/` — that is the feature's permanent record.

## Quality gates (CI)

Blocking on every PR: tests · patch coverage ≥ 80 % on changed lines · **ratchet** (lint and complexity/size violations may not exceed `main` — brownfield repos adopt the rules without a big-bang cleanup; `ruff` becomes fully blocking once a repo is clean) · pr-doc present (an `openspec/changes/<x>/` for any code change) · gitleaks. Non-blocking until a repo's debt is paid: mypy. Limits: ≤ 50 statements per function, complexity ≤ 10, ≤ 400 lines per file (a repo may set stricter).

## Definition of done

Tests for every new function or class, none deleted or skipped · lint, types, ratchet green · full pipeline run on an example, output attached · real-hardware run with evidence when the change touches a robot, sensor or firmware · docs level(s) updated, decision recorded as an ADR when durable · out-of-scope findings filed as issues · agent review passed (its table on the PR) · one owner approval.

## Restricted without explicit human approval

`.github/workflows/`, lockfiles, `infra/`, `deploy/`, migrations, secrets, `vendor/` and `third_party/`, anything that runs on a robot, and on forks every upstream file (our changes live in owned paths or `patches/`).

## What we deliberately do not do

No per-person activity reports. No custom SDD tooling. No backlog file (Issues are the backlog). No mandatory slides. No three-reviewer rule. Nothing in this standard that a maintained open-source tool already provides.
